== Overview

Implement High Availability (HA) support for the LRA (Long Running Actions) Coordinator to enable fault-tolerant distributed transaction coordination across multiple coordinator instances. Currently, while multiple LRA coordinators can run in parallel for horizontal scaling, each coordinator manages only the LRAs it creates due to isolated, non-distributed storage. This restriction means that if a coordinator instance fails, its LRAs cannot be managed by other coordinators, creating availability and fault-tolerance issues.

This proposal introduces distributed storage using Infinispan to enable any coordinator instance to manage any LRA, regardless of which coordinator originally created it. Combined with a Raft consensus algorithm for network partition handling and consistency guarantees, this enhancement will enable true high availability where coordinator failures do not result in lost or unmanageable LRAs. This is particularly critical for cloud-based environments where instances can be ephemeral and failover must be automatic and transparent.

== Requirements

=== Hard Requirements

* **Shared LRA Management**: Enable any Coordinator.java instance to manage any LRA, regardless of which coordinator originally created it
** Any coordinator can handle operations (join, leave, close, cancel, status) for any LRA
** Remove the current restriction where only the creating coordinator can manage an LRA
** Critical for cloud environments where coordinator instances may be replaced or scaled dynamically

* **Distributed Storage Backend**: Integrate Infinispan as the distributed storage mechanism for LRA state persistence, replacing the current isolated storage (file-based or in-memory)
** Store LRA metadata (ID, status, participants, timeouts) accessible by all coordinator instances
** Store participant information and compensation/completion endpoints in shared caches
** Ensure ACID properties for LRA state transitions across the cluster
** Enable atomic reads and writes from any coordinator instance

* **Consensus Algorithm Implementation**: Implement Raft consensus algorithm to handle network partitions and ensure cluster-wide agreement on:
** Leader election among coordinator instances
** LRA state transitions and ownership
** Cluster membership changes
** Split-brain scenario prevention

* **State Synchronization**: Ensure all coordinator instances have a consistent view of:
** Active LRAs and their current status
** LRA participant lists and their endpoints
** Pending operations and timeouts
** Recovery state across the cluster

* **Unified Recovery Management**: Enable a single recovery manager to recover LRAs across multiple coordinator instances
** Current limitation: each coordinator requires its own object store, with one recovery coordinator per store
** Goal: shared storage allows any recovery manager to handle LRAs from any coordinator instance
** Recovery operations (completing failed compensations/completions) can be performed by any coordinator
** Maintain recovery coordinator URL endpoints while making the implementation transparent

* **Failover Support**: Automatic failover when a coordinator instance fails:
** In-flight LRA operations must be recoverable by surviving instances
** No loss of LRA state or participant information
** Pending compensations/completions must be executed by takeover instances
** Particularly important in dynamic cloud environments where coordinator instances are ephemeral

* **LRA Identification**: Enhance LRA ID structure to support shared storage:
** Embed coordinator node ID in LRA identifiers to enable proper routing and recovery
** Maintain compatibility with existing LRA ID format and participant expectations
** Enable coordinators to identify and route operations appropriately

* **Load Distribution**: Distribute LRA coordination workload across available instances:
** New LRA requests can be handled by any coordinator instance
** Any coordinator can process operations for any LRA (not just the creating coordinator)
** Participant callbacks distributed across the cluster
** Recovery and timeout operations balanced across instances

* **Cluster Discovery**: Automatic discovery and registration of coordinator instances:
** Support for static configuration (predefined cluster members)
** Support for dynamic discovery in containerized environments
** Integration with Kubernetes/OpenShift service discovery mechanisms

=== Nice-to-Have Requirements

* **Read Replicas**: Support for read-only coordinator instances that can serve status queries without participating in consensus

* **Metrics and Monitoring**: Cluster health metrics including:
** Coordinator instance status and leader information
** Replication lag and consensus latency
** LRA distribution across instances

* **Graceful Shutdown**: Coordinated shutdown process that:
** Drains in-flight LRAs before terminating
** Transfers leadership to another instance
** Prevents new LRA assignments during shutdown

* **Multi-Datacenter Support**: Extended Raft implementation supporting geographically distributed coordinator clusters with configurable consistency vs. latency trade-offs

* **Rolling Upgrades**: Support for upgrading coordinator instances without cluster downtime:
** Version compatibility checking
** Gradual rollout with mixed versions
** Automatic state migration

* **Backup and Restore**: Cluster-wide backup and restore capabilities for disaster recovery

=== Non-Requirements

* **Application-Level Changes**: Existing LRA applications should not require code changes to benefit from HA coordinators

* **LRA Specification Changes**: No modifications to the MicroProfile LRA specification are required

* **Client-Side Clustering Logic**: LRA clients should use standard load balancing (e.g., Stork library) to distribute requests; client-side cluster awareness is not required

* **Synchronous Replication Guarantees**: While consistency is required, this proposal does not mandate synchronous replication for every operation (eventual consistency with bounded staleness is acceptable for non-critical operations)

== Backwards Compatibility

* **Configuration**: New HA configuration should be optional; single-instance deployments must continue to work without Infinispan or clustering configuration

* **Storage Migration**: Provide migration path from existing isolated object stores (per-coordinator) to shared Infinispan distributed storage:
** Migration utilities to consolidate LRA state from multiple object stores into Infinispan
** Handle LRA ID format migration (embedding node IDs if not already present)
** Support for gradual migration without downtime
** Preserve recovery coordinator URLs and participant endpoints

* **API Compatibility**: All existing REST endpoints and JAX-RS annotations must remain compatible

* **Client Compatibility**: Existing LRA clients (both annotation-based and programmatic) must work without modifications

== Security Considerations

* **Cluster Authentication**: Coordinator instances must authenticate with each other to prevent unauthorized nodes from joining the cluster:
** Shared secret or certificate-based authentication
** Integration with WildFly Elytron security framework

* **Infinispan Security**: Secure communication between coordinator instances and Infinispan cluster:
** TLS encryption for data in transit
** Authentication and authorization for cache access
** Support for encrypted storage at rest

* **Raft Protocol Security**: Ensure Raft consensus messages are authenticated and encrypted to prevent:
** Man-in-the-middle attacks on leader election
** Tampering with state replication
** Unauthorized leader election attempts

* **Network Isolation**: Support for network policies to restrict cluster communication to authorized networks in Kubernetes/OpenShift environments

* **Audit Logging**: Enhanced logging for cluster events:
** Leader election and failover events
** Instance join/leave operations
** Consensus failures and split-brain detection

== Release Note Content

High Availability support for LRA Coordinator enables fault-tolerant distributed transaction coordination through clustered coordinator instances. Key features include:

* Multiple coordinator instances running concurrently with automatic failover
* Distributed state storage using Infinispan for shared LRA metadata
* Raft consensus algorithm implementation for network partition handling and leader election
* Automatic cluster discovery and dynamic membership management
* Zero downtime deployments with rolling upgrade support
* Full backward compatibility with existing single-instance deployments

This enhancement enables production deployments requiring high availability and horizontal scalability for LRA-based distributed transactions in cloud-native environments.
